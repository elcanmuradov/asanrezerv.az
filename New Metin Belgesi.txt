1. Unutduğun və ya Əlavə Etməli Olduğun Service-lər
Siyahın çox yaxşıdır, lakin enterprise səviyyəli bir SaaS üçün aşağıdakılar mütləqdir:
API Gateway (Spring Cloud Gateway): Bütün client-lərdən (Web, Mobile) gələn istəkləri qarşılayan, Rate-Limiting, Routing və Authentication (Token validation) edən qapı.
Search / Catalog Service: "Restoranlar siyahısında görünmə" və axtarış (məsələn: "İtalyan mətbəxi, Nərimanov, boş masa olan") üçün Elasticsearch və ya Meilisearch üzərində qurulan ayrıca servis.
Menu Service (Opsional, amma tövsiyə): Restoranların menyuları, kategoriyalar, məhsullar və şəkillər. restaurant-service-i çox şişirtməmək üçün bunu ayırmaq daha məntiqlidir.
Config & Discovery Server: Kubernetes istifadə etmirsənsə, Consul və ya Nacos (servislərin bir-birini tapması üçün).
2. Tech Stack (Tech Lead Tövsiyəsi)
Dil & Framework: Java 21 (Virtual Threads üçün), Spring Boot 3.3+ / 4.x, Spring Cloud.
Database:
PostgreSQL: Əsas relasional məlumatlar (Auth, Staff, Reservation, Subscription).
MongoDB: Restoran menyuları və filialların dinamik masa planları (JSON sənədləri üçün idealdır).
Caching & Distributed Locks: Redis (Masa rezervasiyalarında "Double-booking" - yəni eyni masanın 2 nəfərə satılmasının qarşısını almaq üçün Redisson Distributed Lock istifadə edəcəksən).
Message Broker: Apache Kafka (Servislərin bir-biri ilə asinxron danışması üçün. Məsələn: Ödəniş uğurlu oldu -> Kafka -> Subscription aktivləşdi -> Restaurant Service xəbərdar oldu).
Search Engine: Elasticsearch (Restoran axtarışı və filtrlənməsi üçün).
Security: Keycloak (OAuth2 / OIDC) və ya Spring Authorization Server.
Observability: OpenTelemetry, Prometheus, Grafana, Jaeger (Distributed tracing üçün).
Infrastructure: Docker, Kubernetes (K8s), Terraform.
3. Subscription-Service (Dərin Təhlil)
Bu servis sənin SaaS biznes modelinin ürəyidir. O, təkcə ödənişi yox, həm də "Feature Gating" (limitlərin idarə olunması) funksiyasını daşıyır.
Entity-lər (PostgreSQL):
Plan: (id, name, max_branches, max_tables_per_branch, visibility_level, monthly_price).
Subscription: (id, restaurant_id, plan_id, start_date, end_date, status [ACTIVE, PAST_DUE, CANCELLED]).
QuotaUsage: (restaurant_id, current_branch_count, current_table_count). Bu entity Redis-də də tutula bilər ki, sürətli olsun.
Invoice / Transaction: Ödəniş tarixçəsi.
Əsas Feature-lər və Logika:
Quota Enforcement (Limit Yoxlanması):
restaurant-service yeni filial və ya masa əlavə etmək istəyəndə, mütləq subscription-service-ə (və ya Kafka eventinə) sorğu göndərməlidir.
Sual: "Bu restoranın Premium paketi var? Əgəri yoxdursa və 3 filialı varsa, 4-cü filialı əlavə etməyə icazə vermə."
Event-Driven Visibility:
Abunəlik bitdikdə və ya ödəniş uğursuz olduqda, subscription-service Kafka-ya SubscriptionExpired eventi atır.
restaurant-service və search-service bunu dinləyir və həmin restoranı dərhal "Görünməz" (is_active = false) edir.
Webhook Handling: Stripe, PayTabs və ya yerli payment gateway-lərdən gələn webhook-ları qəbul edib statusları yeniləyir.
Grace Period (Amnistiya müddəti): Ödəniş kartından pul çəkmək uğursuz olarsa, sistemi dərhal bağlamaq əvəzinə 3-5 gün "Grace Period" verilməsi.

4. Reservation-Service (Dərin Təhlil)
Bu, sistemin ən kritik (highly concurrent) servisidir. Eyni anda 100 nəfər eyni masanı rezerv etməyə çalışa bilər.
Entity-lər (PostgreSQL & Redis):
TableLayout: (id, branch_id, table_number, capacity, shape, coordinates_x, coordinates_y). Frontend-də masaların vizual sxemini çəkmək üçün.
Reservation: (id, table_id, branch_id, customer_name, phone, party_size, start_time, end_time, status [PENDING, CONFIRMED, CANCELLED, COMPLETED]).
TimeSlotConfig: Filialın iş saatları və rezervasiya addımları (məsələn: hər 30 dəqiqədən bir).
Əsas Feature-lər və Logika:
Concurrency Control (Çox vacib!):
İstifadəçi "Rezerv et" düyməsini basan anda Redis Distributed Lock (Redisson) istifadə edərək həmin table_id və time_slot üçün kilid (lock) qoymalısan.
Əgər kilid uğurludursa, DB-də transaction yaradıb, sonra kilidi açmalısan. Bu, "Double Booking" (eyni masanın 2 fərqli adama verilməsi) problemini 100% həll edir.
Dynamic Availability (Dinamik Boşluqlar):
Restoranın qrafikinə və digər rezervasiyalara əsasən boş vaxtları hesablayan optimizasiya olunmuş SQL və ya In-Memory alqoritm.
Hold / Pending Status:
İstifadəçi masanı seçdi, amma hələ təsdiq etmədi. Masa 15 dəqiqəlik "Pending" (Hold) statusunda ona aid edilir. 15 dəqiqə sonra təsdiq olunmasa, Redis-dəki TTL (Time-To-Live) sayəsində masa avtomatik azad olunur.
Waitlist (Növbə):
Əgər masa doludursa, istifadəçi "Waitlist"-ə düşə bilər. Kimsə rezervi ləğv edəndə, notification-service-ə event gedir və növbədəki adama SMS/WhatsApp gedir.
Deposit / Pre-payment Integration:
Premium paketlərdə və ya böyük qruplar (məs: 8+ nəfər) üçün rezervasiya zamanı qismən ödəniş (deposit) tələb olunması.
5. Tech Lead Məsləhətləri (Best Practices)
CQRS Pattern (Command Query Responsibility Segregation):
Reservation-service-də oxuma (Read) və yazma (Write) əməliyyatlarını ayır.
İstifadəçilər boş masaları axtaranda (Read) birbaşa PostgreSQL-ə getmək əvəzinə, Redis-dən (və ya Elasticsearch-dən) oxu. Bu, sistemin yük altında "uçmasını" təmin edəcək.
Saga Pattern (Distributed Transactions):
Ödəniş və Rezervasiya bir-birinə bağlıdırsa, məsələn: "Ödəniş et -> Masa tut". Əgər ödəniş uğursuz olsa, masa tutulmamalıdır. Bunun üçün Choreography-based Saga (Kafka eventləri ilə) istifadə et.
AI Analytics (Sənin qeyd etdiyin Analytics-service):
AI nə edə bilər?
No-Show Prediction: Hansı müştərilərin gəlməyəcəyini proqnozlaşdırıb, overbooking (həddindən artıq rezerv) strategiyası qurmaq.
Table Optimization: Filialdakı masaların yerləşmə sxemini (Layout) AI vasitəsilə optimallaşdırmaq (məsələn: 2 nəfərlik masaları birləşdirib 4 nəfərlik etmək).
Multi-Tenancy (Çoxlu kirayəçi):
Bütün database-lərdə restaurant_id və ya branch_id mütləq tenant_id kimi istifadə olunmalı və hər sorğuda (Hibernate Filter və ya Spring AOP vasitəsilə) avtomatik filter-lənməlidir ki, bir restoran digərinin məlumatını görməsin.
Nəticə
Sənin qurduğun memarlıq çox peşəkardır. subscription-service-i Event-Driven (Kafka), reservation-service-i isə Redis Distributed Lock və CQRS üzərində qurursan, sistem minlərlə eyni anda gələn istəkləri (concurrent requests) heç bir "double-booking" xətası vermədən idarə edəcək.
